# ログイン設計（2026-11-23 Kotaとの合意内容）

## この文書の位置づけ（Kota、2026-11-23 15:54）
- サービスやAIエージェントを乗り換える時の準備。判断と仕様は担当者の頭の中ではなく、この文書とリポジトリ内の運用記録（OPERATIONS.md / LOGIN_SETUP.md）に残し、誰が引き継いでも同じ設計で再現できる状態にする。
- 乗り換え時の要点：イベントデータの正本はシート、サイトのコードはGitHubリポジトリ、会員の同期データはFirestore（memberdata/codes/recovery の単純な文書構造で、JSONとしてそのまま他ストアへ移せる形）。会員コード方式の考え方（アカウント本体＋コード索引＋Q&A復旧索引）は特定サービスに依存しない。

## 前提：編集の本拠はスペース版（Kota、2026-11-23 15:53）
- 更新・修正・手動での新規登録は、基本すべてスペース版ガイドから行う。試作サイト（公開側）は閲覧専用で、編集機能も管理者ログインも持たない。
- したがって試作サイトのログインは、閲覧者の「継続」（推し・お気に入りの端末間維持）専用。将来の役割（アーティスト・主催の自主更新）も、登録の入口はスペース版側の申請フローに置き、公開サイトから直接データは書き換えない。

## 目的（本人確認ではなく「継続」）
- 端末・ブラウザを変えても、推し・お気に入り等の情報が維持されること。
- 更新・修正する人（Kota、アーティスト、主催）が、同じ立場のまま作業を続けられること。
- 個人情報は集めない。ガイドはSNS化しない（プロフィール・フォロー・投稿を持たない）。
- メールアドレスを集めないことは、漏洩の防止そのもの（Kota、2026-11-23 15:47）。運営者も他人のアドレスを保持したくない。会員データが万一出ても、ハッシュをキーにした推し・お気に入りだけで、誰のものか分からない形にしておく。

## 方式：サイト発行の会員コード（Kotaの提案）
- サイトが長いランダムコードを発行し、それ自体がログインの鍵。別端末ではコードを入れるだけ。
- メールアドレス・氏名・Googleアカウント不要。使い捨て可（守る対象は推し・お気に入りだけなので喪失の痛手が小さい）。
- コードはいつでも画面で確認でき、控え（メモ・スクリーンショット）がバックアップになる。
- Googleログインは管理者（Kota）用として併存させる。

## データ方式（Firestore、既存プロジェクト kansai-event-guide を流用）
- アカウント本体は `memberdata/{acct}` に1人1文書（artists/events 配列＋updatedAt＋codeHash＋recoveryHash）。acct はランダム64桁ID。コード原文はサーバに置かない。
- コードの索引 `codes/{SHA-256(コード)} → acct`。コードでログイン＝索引を引いて本体を読む。再発行は索引の差し替え（旧コードは無効化）。
- 1人1文書方式により、読み込みはログイン時1回。10,000人規模でも無料枠（読込5万/日）に収まる設計。
- ルール：memberdata / codes / recovery はいずれも64桁ハッシュのキーを知る者のみ読み書き可。users/{uid}（Google用）は従来ルールを維持。
- コードの推測耐性：20文字・曖昧文字除外の英数字（約100ビット）。

## コードを失くしたとき（Kota、2026-11-23 15:42）
- 本人が決めた「質問と回答」でログインできるようにする。索引は `recovery/{SHA-256(質問:回答)} → acct`。質問・回答は正規化（前後空白除去・小文字化・空白圧縮）して照合。
- 復旧ログイン後はコード未設定状態になり、「コードを再発行」で新しいコードを作る（旧コードは自動で無効化）。
- 質問と回答の設定・変更はログイン中のみ。変更時は旧索引を削除する。
- **同じ質問と回答の組み合わせは登録不可**（Kota、2026-11-23 15:50）：設定時に索引を照合し、他アカウントが使っている組み合わせは弾く（質問か回答を少し変えてもらう）。被りの可能性を仕組みで潰す。
- 紙メモとの相性：ランダムコードは書き写しミスが起きやすいが、質問と回答は自分の文章なので書き間違い・読み間違いのリスクが低く、定期的に変えても忘れにくい（Kotaの指摘）。コード＝機械が持つ鍵、Q&A＝人が覚える鍵、の二層で弱点を補い合う。
- 守る対象は推し・お気に入りであり、この復旧の強度で足りるという位置づけ（Kotaの提案どおり）。

## 本人確認と役割（第2段階）
- 役割は3層：管理者（Kota）／アーティスト・主催／閲覧。
- 本人確認はサイト内で行わず、公式SNS（X・Instagram）経由で外部に済ませる。確認後、Kotaがその会員のコードに役割を付与する（rolegrants はコンソールからのみ書込可、クライアントからは読取のみ）。
- 役割付きコードの喪失時は、本人確認の上でKotaが再発行。
- アーティスト・主催の自主更新・追加は「本人が申請 → Kota承認 → 掲載」の流れで別途設計（既存の掲載・修正依頼の発展）。

## 将来層（保留、ログインが使えることが前提）
- 推しの公開は任意（初期非公開）、仮名のみ、申請制のつながりは作らない。
- 見せ方は個人ではなく集合（同じ推しの人数、集まる現場）。ぼっち参戦・未参戦の人の心理的ハードルを下げる目的。

### ログイン活用アイデア（Kota、2026-11-23 16:52〜16:55、メインチャット発言の転送。設計メモとしての記録であり、実装着工の指示ではない）
- ログインがあるなら、フィードやSNSっぽいタイムライン形式でイベントを見られると面白い。
- TikTokやInstagramのようなUI/UXと合わせて使う形。フライヤー画像中心のカードが流れる見せ方。
- ログインで設定も保持できるようにする。縦スライド／横スライドなど、見やすい表示方法を利用者が選べる形。
- トップページのカスタマイズ機能もあり得る。
- 優先順位（Kota本人の付け方）：「そんなことよりイベントをちゃんと載せろ」— 掲載の完全さが先。これらはログインが実際に使えるようになった後の層として扱う。

## 入口の順序：ログインが先、アンケートは後（Kota、2026-11-23 22:20）
- 指摘：「ログインが継続されても、アンケートが登場して、トップページに行ってからログインする仕組みでは意味がない」— そのとおりであり、順序を正とする。
- 規則：
  1. この端末にログインのセッション（会員コード／Google）がある場合は、アンケートを自動表示しない（2026-11-23 実装：自動表示の条件にセッション有無を追加）。
  2. アンケートの回答（好み）もアカウント同期の対象に含める。新しい端末でログインしたら好みも復元され、アンケートは出ない（現状の同期対象は推し・お気に入りのみ。好みの追加は Firestore 作成後の同期検証とあわせて実装する）。
  3. 初回の入口は「ログイン／会員コード発行 → アンケート（任意・スキップ可）」の順で提示する。アンケートが入口を塞ぐ形にしない。
- アンケートが正しく完了する状態（この順序で一通り動くこと）が、次の機能（当日の朝ポップアップ等）の前提。

### 次に実装したい機能（Kota、2026-11-23 22:20、アンケート完了が前提の設計メモ）
- 推し登録や「気になる」チェックをしているイベントで、当日なのに見落としていそうなものがあれば、その日の朝などにサイト／アプリへアクセスした時点でポップアップメニューで表示する（今日の推し・気になる現場のリマインド）。
- リマインダーには設定を持たせる：表示する時間の指定、オフへの切替ができること。
- 「やりたいことは多いが、問題を1つずつ潰さないことには無理」（Kota）— 着工は入口の順序とログイン維持が通ってから。

## 管理者モード（Kota、2026-11-23 15:52・16:41）
- Kotaは管理者なので、自分の端末ではログイン不要にする。試作サイトの「ログイン・同期」に管理者モードを追加（2026-11-23実装）：端末ごとに、本人が決めたパスフレーズで有効化すると、その端末では以後ログイン操作なしで管理者として扱う（編集フォームの提出者も admin になる）。
- これは端末内にだけ保存される印であり、サーバ側の権限ではない。公開側に守るべき管理データがないため、この形で足りる。Firebaseコンソールやスペース版側のログインは各サービスの仕様で別に存在する。
- 管理者モードでは同期は行わない（端末内保存のみ）。端末間同期が要るときは会員コード/Googleを使う。

## 状態表記とゲスト利用（Kota、2026-11-23 16:50）
- ログイン中かどうか分かる表記にする：ヘッダーのボタン自体が状態を表示する（未ログイン / 同期、ログイン中（同期ON）、ログイン中（会員コード）、ゲスト利用中、管理者モード）。
- ゲスト機能：一時的な端末（共有端末など）で、ログインせず端末内にだけ保存して使う明示的なモード。「ゲスト利用を終了してデータを消す」で、その端末の推し・お気に入りと好み設定を消去して返せる。
- ゲストでもバックアップと引き継ぎは可能にする（Kota、2026-11-23 16:52）：既存の「データ引っ越し」（JSONバックアップの保存・読み込み）はログイン状態に依存しないため、ゲストでもそのまま使える。消去の前にバックアップを取る運用。
- バックアップの外部活用：お気に入りを日付順・詳細つきの文章（行程表テキスト、Markdown）に書き出せるようにし、GPTやGeminiなどの他AIに渡して旅のしおりの下書きなどに使える形にする。データを特定のサービス・AIに閉じない、乗り換え準備の一環。
