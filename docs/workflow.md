# ワークフロー: 書き込み → 反映 → 表示（画像を含む）

関西イベントガイドで「情報を書いてから、利用者の画面に出るまで」の全経路の正本です。
担当AI・担当者が変わっても同じ手順で回せるように書いてあります。掲載ルール自体は `docs/event-listing-rules.md`、サイト設計の定義は `docs/site-design-rules.md` を参照してください。

## 全体像

データの流れは一方向です。

1. **書き込み**: イベント・プロフィールの情報が、後述の経路A〜Dのどれかで入る
2. **正本への登録**: スペース版ガイド（本体）へ登録される。ここが唯一の正本
3. **シート同期**: 本体から公開シート（Googleスプレッドシート）へ同期される（自動ではない。同期を実行した分まで）
4. **表示**: 試作サイト／フィード専用アプリ／公開ミラーがシートを読んで表示する。本体（スペース版）は登録した時点で表示される

報告の作法: 「本体へ登録した」「シートへ同期した」「公開面で表示を確認した」は**別の結果**です。分けて報告し、途中の段階を完了と呼ばないこと。確認できない表示は「未検証」と明記すること（最終判断は運営者 Kota の実機）。

## 経路A: 処理側が本体へ直接登録する（主経路）

Muse など処理側のAIが、一次情報で裏取りした内容を本体へ登録します。

- 登録前に最新の状態（イベント一覧・プロフィール）を取得し、重複を確認する。重複判定は**日付の一致が必須**で、期間イベント（終了日を持つ記録）も含めて照合する（単日分だけの照合は重複登録の原因になる）
- **更新は全項目の再送が前提**（本体の更新は置き換え方式で、省略した項目は初期値に戻る）。更新前に最新の状態を取り、変える項目以外はそのまま含めて送る。楽観ロック（更新日時の一致確認）がある場合は取得時の値を渡す
- 会場名は会場プロフィールのキー（正式名称＋自治体）をそのまま使う。新しい会場は先にプロフィールを作る
- 登録・更新のあとは対象を読み戻し、変えた項目と画像が残っていることを確認してから報告する。欠けていたら更新前の状態から復旧する
- 書き込みは構造化された結果ファイル（調査結果の一覧）から行う。作業途中の要約文を根拠に書き込まない

## 経路B: 外部AI入力タブ（他AIの提案）

他のAI（Arena AI 等）の調査結果は、公開シートの `外部AI入力` タブへ書かれます。ここに書いても**自動では公開されません**。

- 処理側は、運営者から指示があった時点（「シートに書いた」と言われた場合を含む）で即座に全行程を行う: タブを読む → 一次情報で再検証 → 本体へ登録（経路Aの作法）→ シート同期 → タブの処理状況・処理メモを記入
- 夜23時の定期処理が日次バックストップとして残っているが、指示があれば即時処理が優先
- 一次情報で確認できない提案、既存掲載と矛盾が残る提案は「保留」にし、強制登録・上書きはしない

## 経路C: サイトの送信フォーム（利用者・主催者・アーティスト運営からの投稿）

試作サイトの新規登録・修正フォームからの送信です。

- 送信には**ログインが必須**（管理者／会員コード／Google のいずれか）。ログインなしで送れる設計にはしない（運営者の確定指示）
- 送信先は受付メール `kansai-event-info@muse.ai`（FormSubmit経由）。届いた内容を処理側が確認し、経路Aの作法で本体へ登録する
- 送信した人の端末には「反映待ち」として端末内に保存され、その人の画面では先行表示される。他の利用者には出ない
- テスト送信（「登録しないでください」と書かれたもの）は登録しない

## 経路D: プロフィール（アーティスト／会場／主催者）

- アーティスト・会場のプロフィールは本体のデータベースが正本。イベント登録とは別に管理する
- 試作サイトへの反映は**自動**（2026-11-24〜）: 本体へ登録・修正 → シート同期で `artists`／`venues`／`readings` タブへ出る → 試作サイトが読み込み時に同梱データへ重ねる。再pushは不要
- ただしアーティスト／メンバーのアイコン画像は本体内のファイルであり、公開サイトからは参照できない。公開側へ出すには画像ファイル自体の書き出しが別途必要（未実施）
- 会場プロフィールの更新も置き換え方式。全項目（画像キーを含む）を保持して送らないと画像が消える
- 主催者もデータベースの軸として扱い、イベントの主催者欄と連動させる（2026-11-25 対応開始）

## シート同期の手順と注意

- 同期はスクリプト（`write_sheets.py` 系）で本体データを読み、各タブを生成して書き込む。生成タブ: `events`（全項目）／`events_lite`（軽量）／`events_details`（詳細）／`events_images`（複数画像）／`検索辞書`／`artists`／`venues`／`readings`
- 同期は自動ではない。「本体に登録した」と「シートに出た」は別。公開面の数字は同期時点のもの
- シートのグリッド行数には上限がある（各タブ 7,500 行へ拡張済み、2026-11-19）。件数が上限へ近づいたら先に拡張する。上限超過で書き込みが失敗した場合、書けたタブと書けていないタブを切り分けて書き直す
- 件数が減った同期では、末尾に古い行が残ることがある。同期後は行数を確認し、余剰行があれば空白で消して再確認する
- 月別タブへの分割が予定されている。試作サイト側の読み取りは設定ファイル（`assets/sheet-sources.json`）で月別エントリを足すだけで合体読みになるよう準備済み。切替時も閲覧が止まらないことが絶対条件

## 画像のワークフロー

画像は「集める → 本体に保存する → 公開URLを1つ作る → 記録する → 全面で同じURLを参照する」が原則です。

1. **集める**: フライヤーを探す順序は (1) チケット販売ページ (2) 主催の公式アカウント (3) 出演者それぞれの公式アカウント (4) 会場の公式アカウント。原寸を使う。画像が無い登録は「画像待ち」であり完了扱いにしない（詳細は掲載ルール第6節）
2. **本体へ保存**: 登録時に本体へ画像を保存する。更新で画像を変えない場合は画像項目に触らない。付け替える場合は公式URLから取り込み直し、保持すべき全画像を順序に含める。**保存済み画像の内部キーを順序指定に使わない（全画像が消える）**
3. **公開URL化**: 本体内の画像は公開サイトから参照できないため、公開URLを1件につき1つ作って記録する。置き場は3経路: GitHub（原寸のまま。SVGで包んで置く）／Notion／元URLの直参照（切れる前提の保険レーンであり、恒久とは呼ばない）。同じ内容の画像は1ファイルに寄せ、二重にコピーしない。**画質は落とさない**
4. **記録**: 公開URLは移行の記録（`image_migration_state.json`）に1回だけ記録し、シート同期がイベントの画像URLとして各面へ運ぶ。複数画像は `events_images` タブと試作サイト側の `assets/event-images.json` で運ぶ
5. **表示と保険**: 試作サイト・フィードは記録された公開URLを表示する。読み込めなかった場合は、登録時に記録した元の画像URL（一次情報の原URL）へ自動で差し替える保険が働く（サイト v100〜。保険表は `assets/event-image-fallbacks.json`、登録が増えたら再生成する）
6. **死活チェックと修復**: 毎日06:40に全公開URLの死活チェックが走る。切れたURLはその日のうちに別の経路で再公開して修復する（2026-11-25 実績: 12件検出→全件修復）
7. **Notion の制限対策**: Notion への登録呼び出しは短時間の集中が制限の引き金になる。移行は逐次・間隔を空けたドリップ実行（スクリプト `migrate_past_drip.py`、AIトークンを使わない）で行い、制限に当たったら休んで自動続行する。Notion は実際に制限へ達するまで継続する（運営者判断）
8. **退避**: Notion が使えなくなっても、現存イベント分は全件、本体内の原本から再生成できる（実測済み）。開催中・今後分から GitHub 経路で再公開する

## 表示面ごとの反映のされ方

- **スペース版ガイド（本体）**: 登録した時点で表示される。正本
- **試作サイト**: シート同期の後に表示される。読み込みは軽量データ（`events_lite`）を先に表示し、詳細（`events_details`）を後から重ねる。出演者などの詳細項目は詳細の合体が終わるまで空に見えることがある。端末内（IndexedDB）に保存して即表示し、自動の再取得は12時間に1回。「再読み込み」ボタンは12時間ルールを迂回して必ず最新を取る。容量不足時は開催予定のみの軽量版で保存する。プロフィールと検索辞書は読み込み時にシートのタブから自動で重ねる
- **フィード専用アプリ**: 試作サイトと同じデータ・同じ反映タイミング。専用 Service Worker（スコープ /feed/ のみ）を持つ別アプリ
- **公開ミラー**: 埋め込みスナップショット＋シート差し替えの設計だが、編集したら**再共有しないと公開リンクに反映されない**。現在は旧スナップショット（約5,566件）のままで、終了か継続かは運営者の判断待ち

## 検証の作法

- サイトを更新したら、公開面でフッターの版数（動作記録: 版 v○）が新しい版になっていることを確認してから動作を見る。GitHub Pages のキャッシュで最大10分ほど旧版が見えることがある
- 「登録した」「同期した」「表示された」を分けて報告する。検証環境で再現できないものは「未検証」と明記する。運営者の実機の挙動が最終判断
