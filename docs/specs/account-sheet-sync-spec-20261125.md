# アカウント同期を「アカウント用スプレッドシート」方式に作り替える仕様（2026-11-25、Kota決定）

## 決定の経緯
- 同期の保存先だった Firestore が未作成で、全ユーザーの端末間同期が止まっていた。
- Kota の決定（2026-11-25）: 保存先を Firestore から「アカウント専用のスプレッドシート（非公開）」に作り替える。今後は **イベント情報管理のシート** と **アカウント用シート** の2シート運用とする。
- 理由: 管理画面（Firebaseコンソール）不要、運営者（Kota）がデータを見て触れる。

## 構成
- サイト（静的）→ HTTPS POST → Apps Script（入口プログラム、アカウント用シートに紐付け）→ 非公開シートの `kv` タブ（key / json / updatedAt）。
- シートは非公開。サイトから直接は読まない。読み書きは必ず入口プログラム経由で、鍵が合った行だけを返す。一覧取得の操作は作らない（Firestoreルールの「自分の分だけ・一覧不可」と同じ考え方）。
- 入口プログラムのURLはサイトの設定（account-config.js）に公開で置く。URL自体は鍵ではない（安全性は鍵とトークンの照合で担保する。Firestoreの公開設定値と同じ位置づけ）。

## 鍵の設計（行の単位）
- `m:{アカウントID}` 会員コード方式のアカウント本体。アカウントIDは発行時に作るランダム64桁hex。そのIDを知っていること自体が権限（従来の memberdata と同じ）。中身: 推し・お気に入り、userdata（行きたい/気になる/リスト/フォロー/好み等）、codeHash、recoveryHash。
- `c:{SHA-256(コード)}` コード→アカウントIDの索引（従来の codes と同じ）。
- `r:{SHA-256(質問:回答)}` 復旧の索引（従来の recovery と同じ）。
- `g:{SHA-256("kg-google:"+uid)}` Googleログインの人のデータ（推し・お気に入り＋userdata を1行に集約）。この行だけは鍵の知識では足りず、リクエストに付けた Firebase のIDトークンを入口プログラムが Google の tokeninfo で検証し、プロジェクト一致と uid のハッシュ一致を確認する。

## 入口プログラムの操作
- get / set / merge（項目単位の上書き）/ del / favops（推し・お気に入りの追加・削除の並びを1リクエストで原子的（ロック下）に適用）。
- 書き込みは LockService で直列化する。値の上限は約900KB（サイト側の従来ガードと同値）。
- それ以外の操作・形式の違う鍵はエラーにする。

## サイト側（account.js）の変更
- 保存先の呼び出しをすべて入口プログラム経由（kvGet/kvSet/kvMerge/kvDel/favops）に差し替える。Firestore SDK の読み込みはやめる（Googleログイン用の Auth は従来どおり Firebase Auth を使う）。
- 会員コード方式は Firebase が無くても動くようにする（接続先URLが設定されていれば、会員コードの発行・ログイン・復旧・セッション復元を単独で行う）。一般ユーザーの本命ルートを Google 基盤から切り離す。
- 同期の意味は変えない: ログイン時に統合（和集合）で端末データを消さない、変更は45秒間隔＋画面を閉じるときに自動保存、連続失敗時は30分自動停止（v110の回路遮断は維持）。
- 接続先URLが未設定の間は、従来どおり端末内保存のみで動き、会員コードは「準備中」表示になる。

## Kota の設置作業（1回だけ、約10分）
1. アカウント用スプレッドシートを新規作成（共有しない）。
2. そのシートの「拡張機能 → Apps Script」に、配布するコードを貼る。
3. デプロイ → ウェブアプリ（実行ユーザー: 自分 / アクセス: 全員）。
4. 発行されたURLを Muse に渡す → account-config.js に入れて公開する。
手順の詳細は ACCOUNT_SHEET_SETUP.md。

## 保険として Firestore も併用する（Kota追記、2026-11-25 19:22）
- 「何かあってログインと同期がうまくいかなかった時の保険に Firestore も」という Kota の指示で、保存先は二重化する。
- 主軸はアカウント用シート。書き込みはシートへ先に書き、同じ内容を Firestore へも best-effort で書く（二重書き込み）。読み込みはシートを正とし、シートが失敗したときだけ Firestore から読む。
- Firestore 側の失敗は利用者の操作を止めない（保険側の未送信分は専用の待ち行列に残し、復旧したときに流す。会員コード側の保険書き込みは状態まるごとの再送で追いつく）。
- したがって Firestore の作成とルール公開も依然として必要（保険が実在するため）。作成手順は LOGIN_SETUP.md のまま。シート側が主軸になったので、Firestore は「保険の置き場」として作る。
- どちらか片方だけが設定されている状態でも動く（シートのみ＝保険なしで稼働、Firestoreのみ＝従来動作）。

## 検証
- 接続後に実地確認: 会員コード発行 → シートに行ができる → 別コンテキストでコードログイン → 推し変更 → もう一方へ反映。Google方式はトークン検証の拒否系（無効トークン）を確認し、正常系は Kota の実機（PC＋スマホ）で確認する。
- Firestore は使わなくなる。LOGIN_SETUP.md は本方式に書き換える（Firestore作成は不要になった）。
