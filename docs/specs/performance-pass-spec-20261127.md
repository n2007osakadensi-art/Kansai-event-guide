# 軽量化仕様（2026-11-27、v219）

## Kotaの指摘
- サイト・アプリが若干重くなってきたので改善を。

## 実測（2026-11-27、gzip転送量＝実際にダウンロードされる量）
- index.html: 214KB（素 822KB）
- events_lite（シート）: 943KB（素 5.06MB）
- events_details（シート）: 1.18MB（素 4.04MB）
- 同梱 assets/venues.json: 531KB（素 1.94MB）
- シート venues タブ: 445KB（素 1.97MB） ← 同梱と同一の会場プロフィール（3,958件）が二重に起動経路へ
- 同梱 assets/artists.json: 23KB／シート artists タブ: 24KB
- 編集系: editor.js 57KB、profile-editor.js 26KB（素。起動ごとに解析されていた）

## 対応
1. **会場プロフィールを起動経路から分離**（loadProfiles から venues.json を外し、loadVenueProfiles / loadSheetVenues を新設）
   - 読み込みのきっかけ: 詳細データ（events_details）の結合が終わった後の applyData／会場DBタブを開いた時／起動20秒後の保険タイマー、のうち一番早いもの。
   - 読み込みが終わったら索引を作り直し、表示中の画面・詳細・プロフィールシートを再描画する（従来のシート側プロフィール到着時と同じ作法）。
   - 会場プロフィールが届くまでの間も、一覧・検索・詳細は従来どおり使える（プロフィールは補助データという既存の位置づけのまま）。検索の会場住所・別名まわりのヒットは、到着後に完全になる。
2. **編集系スクリプトの遅延読み込み**
   - editor.js / profile-editor.js の script タグを外し、開く操作（ヘッダーの「＋ 新規登録・修正」、詳細の編集、プロフィールの編集ボタン）の時に kgLazyScript で初めて読み込む。
   - サービスワーカーの事前キャッシュ（SHELL_FILES）からも外す。初回利用時にランタイムキャッシュへ入る。
   - editor-config.js（949B、設定のみ）は従来どおり。

## 変えないもの
- 画像の画質（従来ルールどおり、軽量化で画質は落とさない）。
- イベントデータの取得量（events_lite / events_details は検索・詳細の完全性に必要なため対象外）。
- account.js（ログイン状態と同期が全体から参照されるため、起動時読み込みのまま）。
- フィード専用アプリ（編集系を持たず、今回の対象は本体のみ）。

## 追加（同日）検索・切り替えの体感改善
Kota追加指摘: 検索やタブ切り替え、ページ切り替えの読み込みも重く、フリーズしたように惑わされることがあった。

### 原因（コード確認）
- 検索は全9,584件について「検索用の文字列（索引）」を組み立てて照合する。索引には出演者の読み・別名・辞書語・メンバー名、会場の住所・別名、タイムテーブル本文まで含むため、1件あたりの組み立てが重い（説明文JSONの解析を含む）。
- プロフィールやタグなどデータが届くたびに、索引キャッシュを全件消去していた。起動直後は到着が何度も続くため、そのたびに次の検索で全件組み立て直し＝数秒止まって見える。
- 候補（サジェスト）表示はキー入力のたびに同期実行され、全件走査していた（結果の描画側は既に110ms遅延あり）。

### 対応
- 索引に世代番号（hayEpoch）を付け、無効化は「世代を進める」だけに変更。実体の組み直しは裏側の事前作成（kgWarmHay: アイドル時間に約24msずつ分割して全件を温める）が担い、検索時はほぼ温まった索引を使う。世代が進んだら再び温め直す。
- 出演者ごと・会場ごとの索引部品をキャッシュして使い回す（hayPerfFrag / hayVenueFrag）。同じ出演者・会場は全イベントで共有されるため、組み立て回数が激減する。
- 説明文JSONの解析結果をイベントにキャッシュ（ev._pd）。
- 候補表示を既存の110ms遅延に相乗りさせ、キー入力ごとの全件走査をやめた。
- 検索でヒットする中身（索引文字列）は変更前と完全一致することを、旧実装との機械比較で確認した（会場プロフィール＋タイムテーブル＋タグ付き／通常説明／出演者なしの3ケース＋世代更新の再構築）。
