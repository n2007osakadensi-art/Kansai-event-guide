# 初回読み込み軽量化（lite先行表示）仕様 — 2026-11-23

## 目的
- Kotaの現在の不満は「開くのが遅い」「まれに落ちる」の2点（2026-11-23 22:11）。
  デザイン・機能の不満は無く、改善指示はその都度。先行して直すのは表示速度と安定性。
- 画質は落とさない（同日 22:09 の指示）。対策は読み込み構造のみ。

## 現状（実測 2026-11-23 22:1x、gviz生JSON）
- events（全26列）: 6.76 MB — 初回はこれを全部取得・解析してから表示。
- events_lite（19列）: 3.69 MB — id,title,date,dateEnd,timeLabel,startMin,endMin,
  venue,area,prefecture,category,categories,price,imageUrl,venueSpaceNote,
  isFree,priceClass,views,impressions。一覧・カード・タイトル/会場/カテゴリ検索に足りる。
- events_details（8列）: 3.32 MB — id,performers,description,linkWeb,linkTicket,
  linkX,linkInstagram,organizerName。出演者・詳細・リンク・主催者はこちら。

## 方式
1. 初回（キャッシュ無し）: events_lite を先に取得して一覧を即表示する。
   続けて events_details を取得し、idで結合して静かに差し替える（現行の
   バックグラウンド更新と同じ作法で、通知は出さない）。
2. 結合完了後は従来どおり全データを IndexedDB に保存し、オフライン表示・
   12時間ルール・再読み込みボタンの挙動は変えない。
3. キャッシュがある場合は従来どおりキャッシュ即表示が最優先。更新取得は
   lite→details の順で行い、details 取得までは既存キャッシュの詳細を保持する。
4. 失敗時の縮退:
   - lite 取得失敗 → 従来の events 全件取得にフォールバック。
   - details 取得失敗 → lite のまま使える状態を維持（詳細・出演者は未表示の旨が
     分かる状態にし、再読み込みで再試行できる）。一覧・検索（タイトル等）は止めない。
5. 過渡期の検索: lite のみ表示中は出演者名・説明文での検索はヒットしない
   （タイトル・会場・カテゴリ・エリアは通常どおり）。結合完了後は全検索が効く。
   数秒の過渡期として許容する。
6. 編集フォームの読み込み（KGEditorBridge）: details 未結合の間は部分データを
   渡さず「詳細データを読み込み中」と返す（不完全な提案送信を防ぐ）。

## 変えないもの
- 登録データ、シートのタブ構成、同期（write_sheets.py）。
- 画像の画質・サイズ（一切触らない）。
- 検索の照合ルール、絞り込み条件、表示上限（48件/300件）。
- ログイン・会員コード・編集ゲートウェイの仕組み。

## 検証
- 実ブラウザ: 初回相当（キャッシュ無し）で一覧が出るまでの体感と、
  details 結合後にアーティストタブ・詳細・出演者検索が従来どおり効くこと。
- 温キャッシュ再訪で回帰が無いこと（お気に入り・アンケート状態・件数）。
- Kota の実機（iPhone）での開く速さ・落ちる頻度が最終確認。
