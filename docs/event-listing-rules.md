# イベント記載の定義・ルール（スペース版ガイド＋スマホ対応版の統合版）

関西イベントガイドにイベントを載せるときの定義とルールの正本です。スペース版ガイド（本体）の登録ルールと、スマホ対応版（試作サイト／公開ミラー／公開シート）のデータ仕様を1つにまとめました。調査・登録・修正を行うAI・人は、この文書に従ってください。迷ったら「不明」「要確認」と正直に残し、推測で埋めないことが最優先です。

## 1. 掲載の定義（何を載せるか）

- 対象: 関西6府県（大阪・京都・兵庫・滋賀・奈良・和歌山）で開催される、**見に行ける・参加できる**イベント。アイドル／音楽ライブ、ダンス、フードフェス、学園祭、ファッションショー、メンズアイドル、スポーツ、演芸・歌謡、地域のお祭りなど、ジャンルは広く取る。
- 対象に含む: 事前申込制・抽選制のイベント（テレビ・ラジオの公開収録など。申込方法と参加条件を説明に明記する）、ファンクラブイベント、コラボカフェ、交流会・オフ会。
- 対象外: 配信のみのイベント（会場公演＋配信併売は会場公演として載せる）、特典会・ネットサイン会のみのイベント（ライブ等に付随する特典会はそのイベントの一部として記載可）、ポイント還元・抽選会単体・セール等の販売促進のみの催し、一般の観覧ができない招待・当選者限定のみの枠。
- スポーツの線引き（運営者、2026-11-24）: バレーボール・野球・サッカー等の**試合日程そのものは載せない**。ただし試合に付随するゲスト出演・ステージイベントは最優先で載せる。**プロレスの興行は例外として掲載対象**（元アイドル・元グラビア・地域イベント出演者の参加が多いため。試合日程として扱わない）。レッドブル主催・協賛イベント、D.LEAGUE の関西拠点チーム・元Dリーガー・関連ダンスイベント、おもてなし武将隊・忍者隊・殺陣／侍パフォーマンス、東映太秦映画村の公演系イベントは、発見経路・チェック対象として扱う。**相撲は未決定**（運営者の判断が出るまで載せない）。
- 近日分だけでなく、12月以降など**先のスケジュールまで**調査・登録を届かせる（運営者、2026-11-24。全分野共通）。
- 存在が公式（主催・会場・出演者）の告知で確認できたら、詳細が揃っていなくても先に載せる。月間スケジュールに日付だけある公演も、共演者や主催側から詳細を拾って載せる対象にする。未確定の項目は「不明」「要確認」と書く。

## 2. 裏取り（一次情報とすり合わせ）

- 基本は一次情報: 主催・会場・出演者の公式サイト／公式SNS、チケット販売ページ。会場の公式スケジュールだけでなく、会場の公式X・Instagramも確認する（Webで読めない会場がある）。会場側が静かな公演は、主催・出演者側の告知を確認する。
- 公式情報だけでは詳細が足りない場合は、主催・会場・出演者の告知とニュース記事を複数集めてすり合わせ、**一致した内容を確定として書く**。情報源同士で矛盾が残る部分は「要確認」のまま残す。検索結果の要約は根拠にしない（フライヤー画像や既存掲載と食い違うときは一次情報で再確認する）。
- 運営者（Kota）が直接確認して入れた内容や既存の掲載内容を、調査結果だけで上書きしない。一次情報で再確認しても食い違いが残る場合は、既存を残して「要確認」として運営者に上げる。
- mixi は告知の一次情報として使わない。
- 運営者の指示文や略記は、文字どおりに照合しない。入力の都合で略された表記（例: 「EBIDAN」と書かれていても正式表記は「EBiDAN OSAKA」）は、文脈と既存登録から**公式表記へ解決してから**照合する。略記のまま「無い」と判断するのは認識段階の失敗であり、掲載漏れと同じ扱いにする（運営者、2026-11-24）。
- 特例: 清水久美子／KMS Records ★STARS（運営者確認、2026-11-24）。公式サイトは予定一覧のみで詳細が薄く、更新も不定期。詳細（時刻・料金・会場）は会場・主催の告知や共演者の告知（月間予定ポスト等）から取る。単独イベントは**時刻・場所・イベント内容が分かれば十分**とし、存在しないチケットリンクを追わない。

## 3. 必須チェック経路（「要確認」「公演なし」の前に全経路）

項目を「要確認」のまま残す判断も、イベントが「存在しない・公演なし」と結論する判断も、**次の全経路を確認した後でなければしてはいけません**。会場公式サイトだけで止めることが、掲載漏れと詳細不足の最大の原因です（運営者、2026-11-23）。

1. 会場の公式サイト（スケジュール／公演ページ）
2. 会場の公式X（プロフィールではなく、個別の公演告知ポストまで）
3. 会場の公式Instagram
4. 主催の公式SNS・公式サイト
5. 出演者全員の公式SNS（X・Instagram）。タイムテーブル、チケットの取り置き方法、主催者名、撮影可否などは、ここにしか出ないことが多い
6. チケットサイト全部（TIGET、LivePocket、イープラス、TicketDive、および上記の情報源が案内する販売ページ）。1サイトだけ見たことは「チケットサイトを確認した」ことにならない

- 確認した経路ごとの結果（確認した／何が見つかった／見つからなかった）を、調査の結果記録に必ず残す。経路ごとの記録がない「未確認」は、完了として報告しない。
- 会場のスケジュールページが読めない場合は、会場の公式Xとチケットサイトで同じ公演を確認してから「未掲載」と判断する。
- 繰り返し告知する会場・アーティスト・シリーズは、定期チェックの登録簿に経路と頻度を加え、次回は運営者が気づく前に見つけられるようにする。
- 定期イベントのチェックとショッピングモールのイベントページ巡回は、**AIが担う前提**（運営者、2026-11-24: 運営者側の手動巡回は衰えている）。登録簿（調査クローラー管理）に載せて体系的に回し、運営者の申告を待たない。

## 4. タイトル

- タイトルは主催が宣言する**公式名そのまま**。年号・回数（第○回・vol.○）・副題・地域タグを、一次情報に無いのに足さない。複数の公式表記（例: 公式概要の名称とニュース見出しの表記）を組み合わせて1つのタイトルにしない。回数などの付帯情報は説明・備考に書く。
- 既存掲載のタイトルに装飾が付いている場合は、一次情報で再確認してから直す。装飾が本当に公式表記の一部なら、根拠を記録してそのまま残す。
- 検索で見つけやすくするための表記ゆれ対応は検索側の機能であり、登録タイトルを変える理由にはならない。

## 5. 項目の定義（公開シート `events` の列に対応）

スマホ対応版はこの列をそのまま読み込んで表示します。1件のイベントは次の項目で構成されます。

| 項目 | 定義・書き方 |

| title | 公式名そのまま（第4節） |

| timeLabel | 表示用の時刻ラベル（例「開場17:30／開演18:00」「10:00〜16:00」）。不明なら空にせず分かる範囲で |
| startMin / endMin | 開始・終了の分換算（0:00=0）。タイムテーブルの並び順・「回せる現場」判定に使う。時刻が確定している公演は必ず入れる |
| venue | 会場の正式名称＋自治体（例「BIGCAT」「エスタシオンホール（和歌山市）」）。会場内スペースは venueSpaceNote に分ける |

## 6. 画像の集め方

- 登録経路で文章だけが得られ、画像が付かなかったイベントは「完了」ではなく「画像待ち」として扱い、画像が付くか構造的な例外が記録されるまで、画像待ちの一覧に残す。
- フライヤーを探す順序: (1) チケット販売ページ、(2) 主催の公式アカウント、(3) 出演者それぞれの公式アカウント、(4) 会場の公式アカウント。見つけたら原寸の画像URLを使う。
- フライヤーがXにしか出ていない告知は、元のポスト自体を読んでから画像を使う。
- 画像を付けたら対象イベントを読み戻し、画像が実際に付いていることを確認してから報告する。
- 全ての出演者・主催のアカウントを確認しても公式画像が存在しない場合は、理由と確認したアカウントを記録して「構造的な例外」とし、「画像あり」と報告しない。
- 調査の一括報告は画像の確認が終わってから行い、登録件数・画像待ちの件数・画像待ちのIDを同じ報告に含める。

## 7. 重複・分割・統合のルール

- 同一イベントの判定には**日付の一致が必須**。日付・会場・公演名・部・出演者で照合する。
- 1部・2部、出演者や内容が違うものは別件として分ける。同じ公演のVIP枠などの席種違いは1件に統合する。
- 複数ステージ・複数会場は、ステージ別タイムテーブルの形で1件に記載する。ステージが違うだけを理由に分けない。
- 期間イベント（dateEnd を持つ記録）があるところに単日記録を重ねない。分割前に既存の期間記録を確認する。
- 表記ゆれだけが違う重複は正式表記側に統合する。ただし複数日にまたがるイベント同士は統合しない。
- 会場プロフィールも同じ考え方: 表記ゆれだけが違う同一会場の重複は正式表記側へ統合してよい（2026-11-25 に重複48件を統合し 3,587→3,539件、参照ゼロ・画像欠損なしを検証済み）。ただし**閉館・改名した会場はアーカイブとして残し、統合・削除しない**。

## 8. 中止・変更の扱い

- 中止になったイベントは**削除しない**。タイトル先頭に「【中止】」を付け、理由と告知の出典を備考に残す。代替開催は別件として載せる。
- 急な中止・欠席の速報自体はSNSの役割であり、サイトは掲載と一次情報へのリンクが役割。中止が公式に確認できたものは上記の形で反映する。

## 9. 同時開催の相方イベント

- 同じ主催・同日・同会場で別々に載る相方イベント（例: マルシェとその音楽ステージ）は、統合せず別掲載のままにする。ただし全件に主催者欄を同一表記で必ず埋め、説明・備考に同時開催の相方を明記する（詳細画面の「同じ主催・同日」導線で相互にたどれるようにするため）。主催者欄が空の相方は記載漏れとして扱う。

## 10. 更新の作法（データを壊さない）

- 更新は**全項目の再送が前提**（本体の更新は置き換え方式で、省略した項目は初期値に戻る）。更新前に最新の状態を取得し、変える項目以外はそのまま含めて送る。
- 画像を変えない更新では画像項目に触らない。画像を付け替える場合は、公式URLから取り込み直し、保持すべき全画像を順序に含める。保存済み画像の内部キーを順序指定に使わない（画像が消える）。
- 更新後は対象イベントを読み戻し、変えた項目と画像が残っていることを確認する。欠けていたら更新前の状態から復旧する。

## 11. 他AIの入力経路（`外部AI入力` タブ）

他のAIが調査結果を持ち込む場所は、公開シートの **`外部AI入力` タブ**です。ここに書いても自動では公開されません。処理側（Muse／運営者）が一次情報で再検証し、本体へ登録し、シートへ同期して初めて掲載されます。

列の定義（左から）: 処理状況（処理側が記入。提案側は空でよい）／対象イベントID（修正提案のとき）／イベント名／開催日／終了日／時刻ラベル／会場／会場補足／カテゴリ／料金／出演者／詳細・タイムテーブル／チケットリンク／公式リンク／画像URL／指摘・提案内容／根拠URL（一次情報のURLを必ず入れる）／記入者（AI名・担当名）／記入日時／処理メモ（処理側が記入）。

書き方:

- 1行 = 1イベント（または1件の修正提案）。新規は対象イベントIDを空にし、指摘・提案内容に「新規」と書く。
- 根拠URLが無い提案、一次情報で確認できない提案は「保留」になり、強制的に登録されることはありません。
- 既存掲載との重複チェックは、最新の `events_lite` と `外部AI入力` の両方を見て行う。

## 12. 検索・表示側の前提（スマホ対応版）

データの書き方に影響する、表示側の確定仕様です。

- 検索は「入力した文字列のまま」が原則。入力の自動変換・自動置換・自動分割はしない。表記ゆれ・読み（例: KOBerrieS♪＝コウベリーズ）への対応は、検索辞書（シートの `検索辞書` タブ）と読みデータによる内部マッチと候補提示で行い、登録データ自体は公式表記のままにする。
- 話数・回数（vol.○等）に公式番号が無い場合、表示側は「ガイド集計」と明示する。登録側は公式に無い番号をタイトルへ入れない（第4節と同根）。
- 候補（サジェスト）は検索の**補い**であり、検索の意味を変えない。終了済みの除外や期間フィルタの扱いは、候補選択でも手入力でも同一にする。ヒットが終了分だけの場合は、終了分を表示してその旨を明示する（サイト v103 で確定）。
- 推しの照合は候補選択と同仕様にする（別名・正式名の展開、グループ⇔メンバーの相互展開）。完全一致のみの照合は不具合として扱う（サイト v104 で確定）。
- 端末内のお気に入り・推し・リスト・フォローは**本人の端末の中だけ**の情報であり、公開したり集計して他人に見せたりしない（サイト v106 のマイページもこの前提で設計されている）。
- 並び順と「回せる現場」（今から間に合う判定）は startMin／endMin と会場位置で決まるため、時刻と会場の正確さが表示品質に直結する。
